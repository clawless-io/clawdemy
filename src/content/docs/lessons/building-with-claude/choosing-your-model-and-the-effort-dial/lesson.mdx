## Why this lesson

Lesson 1 had you pass one model ID without discussing it. Lesson 2 had you log *usage* with every call. This lesson is the conversation about which model ID is the right one and why, with the parameters that change what one call costs and what it can do.

Model choice compounds. Every call your application makes runs against the model you chose; every dollar of your bill, every millisecond of your tail latency, every "the model got this wrong" complaint traces back to that one line of configuration. The decision is not "use the most capable model everywhere": the top tier is the most capable, but a chat application that runs every user message through it will burn the cost-per-user margin most teams need to keep, and a long-running agent that uses the top tier where the fastest tier would have worked turns a small evaluation bill into a much larger one. The decision is "what does this specific call need, and what is the cheapest model that delivers it."

This lesson covers the four pieces of that decision: **the model tiers and how they actually differ**, **the model-ID convention** (so production code pins what it expects to run), **the effort parameter** (the dial that controls how many tokens Claude spends on a call, on the models that support it), and **adaptive thinking** (the recommended mode wherever a model offers it) versus the older manual extended-thinking mode.

## The model tiers

Anthropic organizes its models into named families, and each family fills a tier. The flagship tier is built for heavy, extended jobs, such as coding agents. Below it, the balanced tier trades a little capability for speed and price; the docs pitch it as the best mix of speed and intelligence. At the bottom, the fastest and cheapest tier is aimed at work where volume and speed matter most, such as sorting, pulling fields out of text, and sending each request to the right place. The lineup can also include a tier above the flagship, built for the hardest reasoning and for agent work that runs over long stretches.

The price gap between tiers is the easiest mental model. Each step down a tier costs less per token, but the steps are not even, and they shift when the lineup changes, so work out the ratios from the table on the day you build. Knowledge cutoffs can differ between models too (the table lists them), so a model in one tier may know less about recent events than another.

The capability ordering is not a hard ranking on every task. A smaller tier often handles a well-scoped task as well as a bigger one; the gap tends to show on multi-step reasoning, complex coding, and nuanced analysis. The balanced tier is not a slightly worse flagship; it is the right choice for production workloads where the flagship is overkill and the fastest tier is borderline.

## How to pick

A working rule, in increasing order of how much you should think about it:

**Start where the docs point, then let evaluation move you.** Before you have an evaluation set, start with the model the docs recommend for most workloads (the table names it), at the right effort level (more on effort below). Once you have an evaluation set, try one tier down. The balanced tier costs a fraction of the flagship per token and runs faster, with intelligence good enough for the bulk of what user-facing applications need.

**Reach for the top tiers when the task is genuinely hard.** Complex reasoning, agentic coding over many steps, work where a wrong answer is meaningfully worse than a slow answer. The most capable models are built for the long-horizon, hard-thinking case. The pricing reflects that.

**Reach for the fastest tier when the task is light and volume matters.** Classification, simple lookups, routing, the inner step of a pipeline that runs millions of times. The fastest tier does plenty of real work, and the savings stack fast on high-volume calls.

**Mix and match inside one application.** A common production pattern is a flagship or balanced model for the user-facing summarizer (where one wrong answer matters), and a fastest-tier model for the inner classifier that decides which summarizer to call (where speed-times-volume is the bottleneck). Lesson 8, From single call to agent loop, and lesson 11, Subagents and Claude Managed Agents, pick this up; the foundation here is that you do not have to pick one model for the whole application.

The decision is rarely "biggest or smallest" in the abstract. It is "what would happen on this specific call if we used the balanced tier instead of the flagship, and is that worth the cost cut?" Build a held-out evaluation set (Track 21 lesson 7 "LLMOps" is the playbook here) and the question gets quantitative: same prompt, both models, measure quality. The cheapest model that passes evaluation is the right model.

## Model IDs: alias versus date-pinned

A small but important detail. Anthropic has used two ID forms over the years, and which one you use in production matters.

**Newer models use a dateless ID that *is* a pinned snapshot.** The ID does not change underneath you; it names one exact version. The Model IDs and versioning page is explicit: "Anthropic does not update the weights or configuration of an existing model ID. When an updated version is available, it ships under a new model ID."

**Older models have a date-suffixed canonical ID and a dateless alias** that resolves to it. The alias is a convenience pointer to the most recent dated snapshot for that version; the dated form is the pinned one. The table below shows which generations use which form, with an example of each. The alias is a convenience for development (you do not have to update the date when a new snapshot lands); the date-pinned form is what production should use, because the alias can resolve to a different snapshot later.

| ID form (as of November 2026) | Used by | Example | Pinned? |
| --- | --- | --- | --- |
| Dateless canonical ID | The 4.6 generation and later | `claude-opus-5-5`, `claude-sonnet-4-6` | Yes; the ID is the snapshot |
| Date-suffixed canonical ID | Models before the 4.6 generation | `claude-haiku-4-5-20251001` | Yes |
| Dateless alias | Models before the 4.6 generation, Claude API only | `claude-haiku-4-5` | No; points to the most recent dated snapshot |
| Source | [Model IDs and versioning](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions) | | |

The practical rule:

- **For new code on a model with a dateless canonical ID:** use the ID as published. It is already pinned, and there is no date suffix to add.
- **For older models in production:** use the date-suffixed form. Behavior pinned; no surprise snapshot changes.
- **For development on older models:** the alias form is fine; you pick up new snapshots automatically.

If your production application calls an older model by its alias and someone reports a regression after a new snapshot lands, the date-suffixed form would have isolated you. It costs nothing to be specific. One caveat from the same page: the serving infrastructure around a model can still change, so small behavior differences can appear on a stable ID.

## The effort parameter

The effort parameter is a dial on token spending per call. It controls how many tokens Claude is willing to spend on a single response, across all the tokens that response includes (text, tool calls, and thinking when it runs). The levels run from *low* through *medium* and *high*, and many models add two higher levels, *xhigh* for long-horizon work and *max* for the deepest possible reasoning. Which levels a model accepts, and which level it uses when you set nothing, differ by model; the tables below list them.

Most models in the lineup support effort. A few older ones do not, and on those, what you get is what the model decides to spend.

The parameter goes in *output_config*, not at the top level:

```python
response = client.messages.create(
    model="claude-opus-5-5",
    max_tokens=4096,
    messages=[{"role": "user", "content": "..."}],
    output_config={"effort": "high"},  # Opus 5.5 defaults to "medium"; this raises it one level
)
```

| Effort level (as of November 2026) | What it does, per the Effort docs | Accepted on |
| --- | --- | --- |
| `max` | Absolute maximum capability, no constraint on token spending | Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5; legacy Opus 4.8, 4.7, 4.6 and Sonnet 4.6 |
| `xhigh` | Extended capability for long-horizon work | Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5; legacy Opus 4.8 and 4.7 |
| `high` | As many tokens as the task needs for excellent results. Default on Fable 5.2 and Sonnet 5.5 (and on legacy models that support effort) | Every model that supports effort |
| `medium` | Balanced, with moderate token savings. Default on Opus 5.5 and Haiku 5.5 | Every model that supports effort |
| `low` | Most efficient; significant token savings with some capability reduction | Every model that supports effort |
| Not supported | Legacy Haiku 4.5 does not accept the effort parameter | |
| Source | [Effort](https://platform.claude.com/docs/en/build-with-claude/effort) | |

The next table lists each model's recommended starting point, per the docs. Two patterns hold across the lineup. First, run an effort sweep on your own evaluation set when you move to a new model, rather than carrying your old setting over; the docs repeat this advice for several models, because the same level name can produce a different amount of work on a different model. Second, at the higher levels, leave a generous maximum-token limit, because thinking and the reply both count against it.

| Recommended starting point (as of November 2026) | Per the Effort docs |
| --- | --- |
| Claude Fable 5.2 | Start with `high` (the default). Step up to `xhigh` for the hardest long-running coding and agentic work where you have measured a gain; step down to `medium` or `low` where evals show quality holds. Reserve `max` mainly for measuring the model's ceiling. |
| Claude Opus 5.5 | `medium` is the default; adaptive thinking is always on, so effort is the main control for reasoning and cost. Run an effort sweep on your own evals rather than carrying settings over from an earlier model. |
| Claude Sonnet 5.5 | Start with `high` unless the workload is agentic or latency-sensitive. Agentic coding and multistep tool use: `medium` for well-specified tasks, `high` for harder or longer ones. Chat and latency-sensitive work: `medium` or `low`. `xhigh` or `max` only where evals show a gain. |
| Claude Haiku 5.5 | Start with `medium` (the default) for most work, including agentic coding. `low` for chat, short tool tasks, and simple high-volume requests. `high` for knowledge work, longer agent tasks, and strict instruction following. |
| Claude Opus 4.8 and 4.7 (legacy) | Start with `xhigh` for coding and agentic use cases; `high` for most other intelligence-sensitive work. The API default is `high`. |
| Claude Sonnet 4.6 (legacy) | `medium` is the recommended default; the API default is `high`, so set it explicitly. |
| Source | [Effort, recommended effort levels](https://platform.claude.com/docs/en/build-with-claude/effort) |

Two practical points. First, setting effort to a model's default level and not setting it at all are equivalent; setting it explicitly is fine but does nothing different. Because defaults differ by model, an explicit setting is also the safest way to keep the same behavior when you swap models. Second, effort affects token spending broadly, including tool calls. At lower levels Claude makes fewer tool calls, combines operations, and proceeds directly to action without preamble; at higher levels it explains plans, makes more calls, and writes detailed summaries. This matters for lesson 8 onward (the agent loop), where total cost is steps times per-step cost.

## Adaptive thinking versus extended thinking

A second parameter close to effort, and a moving target as Anthropic's models evolve. The lesson covers the shape of the choice; treat the docs as the source of truth when the lineup shifts.

**Extended thinking** (also called manual thinking) is the older mechanism. The model produces thinking content blocks before its text response, showing step-by-step reasoning. You enable it by setting the thinking parameter's type to enabled with a budget-tokens value (literal below), and the response includes the thinking blocks alongside the text:

```json
"thinking": {"type": "enabled", "budget_tokens": N}
```

Use cases: complex reasoning, mathematical or logical problems, multi-step planning, anywhere a transparent reasoning trace is useful. The docs mark this mode as legacy. Newer models reject it with a 400 error, a few models still accept it but mark it deprecated, and some older models offer it as their only thinking mode.

**Adaptive thinking** is the recommended mode wherever a model offers it: the thinking parameter with adaptive type (literal below). The model decides when and how much to think, based on the difficulty of the task:

```json
"thinking": {"type": "adaptive"}
```

The model uses the effort parameter as the control. At higher effort levels Claude thinks more often and more deeply; at lower levels it thinks less, and it may skip thinking entirely on easy inputs. On some models adaptive thinking is always on and cannot be turned off, so effort is the main dial you have.

The table below shows what each model accepts.

| Thinking support (as of November 2026) | Thinking types | Default | Rejected with a 400 error |
| --- | --- | --- | --- |
| Claude Fable 5.2 | Adaptive only | Always on | `enabled`, `disabled` |
| Claude Opus 5.5 | Adaptive only | Always on | `enabled`, `disabled` |
| Claude Sonnet 5.5 | Adaptive; `between_tools` turns off up-front thinking | On | `enabled`, `disabled` |
| Claude Haiku 5.5 | Adaptive only | On | `enabled`; `disabled` at `xhigh` or `max` effort |
| Claude Opus 4.8 and 4.7 (legacy) | Adaptive only | Off | `enabled` |
| Claude Sonnet 4.6 and Opus 4.6 (legacy) | Adaptive; extended (deprecated) | Off | None |
| Claude Haiku 4.5 (legacy) | Extended only | Off | `adaptive` |
| Source | [Troubleshooting thinking, per-model table](https://platform.claude.com/docs/en/build-with-claude/thinking-troubleshooting) | | |

For new code, the right pattern is **adaptive thinking plus effort**, not a manual token budget. On an older model that offers only the manual mode, the budget is still the option, and it is worth the use when the task warrants step-by-step reasoning.

## A worked cost example

Concrete numbers fix the abstract. Suppose you are building a feature that takes a user question, classifies it (one of ten categories), then either answers it or routes it elsewhere. Average prompt is 500 input tokens; average answer is 300 output tokens; you expect 100,000 calls per day.

The feature is two calls per request: a classifier (500 input tokens, 20 output) and, for the 70 percent that get an answer, an answer call (500 input, 300 output). Price each leg the same way: multiply the input tokens by the input price and the output tokens by the output price, add the two, and multiply by the number of calls. The table below works three versions at the list prices on the date in its heading: everything on the flagship, everything on the balanced tier, and a mix with the classifier on the fastest tier and the answer on the balanced tier.

| Worked example at list prices (as of November 2026) | Classifier leg: 100,000 calls, 500 in, 20 out | Answer leg: 70,000 calls, 500 in, 300 out | Total per day | Compared with all-flagship |
| --- | --- | --- | --- | --- |
| All flagship (Opus 5.5 at $4 / $20) | 100,000 * ($0.0020 + $0.0004) = $240 | 70,000 * ($0.0020 + $0.0060) = $560 | $800 | Baseline |
| All balanced (Sonnet 5.5 at $2 / $10) | 100,000 * ($0.0010 + $0.0002) = $120 | 70,000 * ($0.0010 + $0.0030) = $280 | $400 | 50 percent cheaper |
| Mix (Haiku 5.5 classifier at $0.10 / $0.50, Sonnet 5.5 answer) | 100,000 * ($0.00005 + $0.00001) = $6 | $280 (as above) | $286 | About 64 percent cheaper |
| Assumptions | Prices per million tokens from the [Pricing](https://platform.claude.com/docs/en/about-claude/pricing) page. A 500-token prompt is under Haiku 5.5's 100,000-token price threshold. | Output counts are assumed to include any thinking tokens, which bill as output. | No caching or batch discount applied. | |

Three things show up in this arithmetic whatever the prices are on the day you read it. The output side dominates the answer leg, because output tokens cost several times what input tokens cost. The classifier leg is all volume and almost no output, so moving it to the fastest tier shrinks it to a small fraction of its flagship cost. And thinking tokens bill as output, so the effort level you choose moves the output side of every leg.

The arithmetic is not exotic. The point is that model choice and parameter choice both move the dial materially. Lesson 7 (prompt caching) and lesson 12 (production cost monitoring) extend the same arithmetic to the cache discount and the org-level dashboards; the foundation here is that the dial exists and is not subtle.

## Common pitfalls

**Defaulting to the top tier on every call.** The most capable model is also the most expensive. A chat-style product that runs every user message through it is paying top-tier rates for traffic a smaller tier could have handled. The fix is evaluation: build a held-out test set, run both models, see what actually drops.

**Using the alias in production on older models.** On the models that have one, the dateless alias is a pointer, and the snapshot behind it can change. Pin to the date-suffixed form in production. (Models with a dateless canonical ID need no date suffix; that ID is already pinned.)

**Forgetting that effort affects tool calls.** Effort is not just "how much text Claude writes." It is total token spend per response, including the tool-call portion. In an agent loop (lesson 8 onward), lowering effort can compound: fewer tool calls per step, terser preambles, less thinking. That can be the right answer for cost; it can also be wrong if the task needs the deeper exploration.

**Swapping models without setting effort.** Defaults differ by model, so a request that leaves effort unset can run at a different level after a swap, with a different cost and a different quality. Set effort explicitly, and rerun your evaluation after any model change.

**Using manual extended thinking on a model that does not support it.** Newer models return a 400 error if you send the manual thinking configuration (the thinking parameter's type set to enabled with a budget-tokens value, literal below):

```json
"thinking": {"type": "enabled", "budget_tokens": N}
```

The replacement is adaptive thinking plus effort. On the few models where manual mode still works but is deprecated, new code should use adaptive too. The thinking table above lists which models are which.

**Mixing model families without evaluation.** Pipelines that route work between models work well when the routing matches capability to need. They fail badly when a fastest-tier step needs to handle flagship-level reasoning and silently produces a worse answer. The eval set (lesson 7 of Track 21) is what tells you the routing is right.

## What you should remember

- **The model tiers:** a flagship, a balanced tier, a fastest and cheapest tier, and sometimes a tier above the flagship for the heaviest reasoning. The table maps family names, IDs, and prices on the date in its heading; the docs are canonical. Start where the docs point, let evaluation move you down a tier, reach for the top tiers when the task is hard, and reach for the fastest tier when volume matters.
- **Mix and match inside one application.** A common production pattern is a flagship or balanced model for user-facing summarization and a fastest-tier model for the inner classifier. Lesson 8 onward extends this into the agent loop.
- **Model IDs:** a dateless canonical ID is already pinned. For older models that also have an alias, use the date-suffixed form in production; the alias is for development.
- **The effort parameter** sits under *output_config*, with levels from *low* up to *max*. It controls token spend per call and affects all tokens, including tool calls. Its default differs by model, so set it explicitly and sweep it on your evals when you change models. The exact request literal sits in the effort-parameter section above.
- **Adaptive thinking** is the recommended mode wherever a model offers it: the model decides when and how much to think, and effort steers it. Manual extended thinking, with a fixed token budget, is the legacy mode: rejected on newer models, deprecated on some, and the only option on some older ones. The exact request literals for both modes sit in the adaptive-thinking section above.
- **Evaluation is how you pick.** Build a held-out test set (Track 21 lesson 7 "LLMOps"), run candidate models against it, pick the cheapest that passes. The decision should be data-driven, not vibes-driven.
