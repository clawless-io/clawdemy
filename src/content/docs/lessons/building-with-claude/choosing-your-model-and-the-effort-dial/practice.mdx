## Self-check

Seven short questions. Answer each before opening the collapsible.

**1. Name the Claude model tiers, what each is for, and (as of November 2026) the model in each tier with its per-MTok pricing pair (input / output).**

<details>
<summary>Show answer</summary>

- **Above the flagship: Fable 5.2** (`claude-fable-5-2`): "For demanding reasoning and long-horizon agentic work" (verbatim, Models overview). **$8 input / $40 output** per million tokens.
- **Flagship: Opus 5.5** (`claude-opus-5-5`): "For long-running agentic coding and knowledge work" (verbatim); the docs suggest starting here for most workloads. **$4 / $20**.
- **Balanced: Sonnet 5.5** (`claude-sonnet-5-5`): "The best combination of speed and intelligence" (verbatim). **$2 / $10**.
- **Fastest and cheapest: Haiku 5.5** (`claude-haiku-5-5`): "For high-volume, latency-sensitive tasks such as classification, extraction, and routing" (verbatim). **From $0.10 / $0.50**, higher for prompts over 100,000 tokens.

Opus 4.8, Opus 4.7, Sonnet 4.6, and Haiku 4.5 are legacy and still available. The tier-to-tier price ratios shift when the lineup changes, so work them out from the [Models overview](https://platform.claude.com/docs/en/models/overview) on the day you build.

</details>

**2. State the pick rule and when you reach for a top tier or the fastest tier instead.**

<details>
<summary>Show answer</summary>

**Start where the docs point** (the model they suggest for most workloads; the flagship as of November 2026), then **let evaluation move you**: once you have a held-out eval set, try one tier down, because the balanced tier costs a fraction of the flagship and runs faster. **Reach for the top tiers** when the task is genuinely hard (complex multi-step reasoning, agentic coding, work where a wrong answer is meaningfully worse than a slow answer). **Reach for the fastest tier** when the task is light and volume matters (classification, simple lookups, routing, the inner step of a high-volume pipeline). A common production pattern is **mix and match**: a flagship or balanced model for the user-facing summarizer, a fastest-tier model for the inner classifier.

</details>

**3. Explain the model-ID convention. When is a dateless ID already pinned, and when is it an alias?**

<details>
<summary>Show answer</summary>

**The 4.6 generation and later** (every current model, plus legacy Opus 4.8, Opus 4.7, Sonnet 4.6, Opus 4.6) use a dateless format that **is** the pinned snapshot. `claude-opus-5-5` and `claude-sonnet-4-6` do not change underneath you; no date suffix is needed. **Pre-4.6 models** (Haiku 4.5, Sonnet 4.5, Opus 4.5, Opus 4.1) have a date-suffixed canonical ID (`claude-haiku-4-5-20251001`) and a dateless alias (`claude-haiku-4-5`) that resolves to the most recent dated snapshot. The alias is a convenience for development (you pick up new snapshots automatically); the date-suffixed form is what production should use, because the alias can resolve to a different snapshot later. For new code on the 4.6 generation, the dateless ID is the right choice; for pre-4.6 models in production, prefer the date-suffixed form.

</details>

**4. The effort parameter: where does it go in the request, what values does it accept, and which models support it?**

<details>
<summary>Show answer</summary>

The parameter goes in `output_config`, not at the top level: `output_config: {effort: "..."}`. Values: `low`, `medium`, `high`, `xhigh`, and `max`. As of November 2026, all five work on the four current models (Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5); among legacy models, `xhigh` works on Opus 4.8 and 4.7, and `max` on Opus 4.8, 4.7, 4.6, and Sonnet 4.6. The default differs by model: `medium` on Opus 5.5 and Haiku 5.5, `high` on the others that support effort. **Legacy Haiku 4.5 does NOT support effort**; there, what you get is what the model decides to spend. Setting effort to a model's default explicitly is equivalent to not setting the parameter at all.

</details>

**5. State the recommended starting points for the effort dial on Opus 5.5 and Sonnet 5.5, and what to do when you move to a new model.**

<details>
<summary>Show answer</summary>

Per the Effort docs (November 2026). **Opus 5.5:** `medium` is the default, and adaptive thinking is always on, so effort is the main control for reasoning and cost; run an effort sweep on your own evals rather than carrying settings over from an earlier model, and set a large `max_tokens` at the higher levels. **Sonnet 5.5:** start with `high` (the default) unless the workload is agentic or latency-sensitive; for agentic coding and multistep tool use, `medium` for well-specified tasks and `high` for harder or longer ones; for chat, `medium` or `low`; `xhigh` or `max` only where evals show a gain. **On any model change:** re-run the effort sweep, because the same level name can produce a different amount of work on a different model, and because defaults differ, set effort explicitly.

</details>

**6. Distinguish adaptive thinking from manual extended thinking. Which models support which?**

<details>
<summary>Show answer</summary>

**Adaptive thinking** (`thinking: {type: "adaptive"}`) lets the model decide when and how much to think, steered by the effort parameter. As of November 2026 it is the only thinking mode on every current model (Fable 5.2, Opus 5.5, Sonnet 5.5, Haiku 5.5) and on legacy Opus 4.8 and 4.7; on Fable 5.2 and Opus 5.5 it is always on. It is also the recommended mode on Sonnet 4.6 and Opus 4.6.

**Manual extended thinking** (`thinking: {type: "enabled", budget_tokens: N}`) is the older mode. The model produces internal *thinking* content blocks before its *text* response, showing step-by-step reasoning. The docs mark it legacy. It is the only mode on **Haiku 4.5**, still functional but deprecated on Sonnet 4.6 and Opus 4.6, and rejected with a 400 error on Opus 4.7 and every later model. For new code, use adaptive thinking plus effort.

</details>

**7. Worked cost question. A feature classifies 100,000 user questions per day (500 input tokens, 20 output tokens for the classifier), then answers 70 percent of them (500 input, 300 output). At November 2026 list prices (Opus 5.5 $4 / $20, Sonnet 5.5 $2 / $10, Haiku 5.5 $0.10 / $0.50 per MTok), what is the per-day cost of: (a) running everything through Opus 5.5, (b) running the classifier on Haiku 5.5 and the answers on Sonnet 5.5?**

<details>
<summary>Show answer</summary>

**(a) All-Opus 5.5.** Classifier: 100,000 calls * (500 input * $4/MTok + 20 output * $20/MTok) = 100,000 * ($0.0020 + $0.0004) = **$240/day**. Answer: 70,000 * (500 * $4/MTok + 300 * $20/MTok) = 70,000 * ($0.0020 + $0.0060) = **$560/day**. Total: **$800/day**.

**(b) Mix.** Classifier (Haiku 5.5; a 500-token prompt is under its 100,000-token price threshold): 100,000 * (500 * $0.10/MTok + 20 * $0.50/MTok) = 100,000 * ($0.00005 + $0.00001) = **$6/day**. Answer (Sonnet 5.5): 70,000 * (500 * $2/MTok + 300 * $10/MTok) = 70,000 * ($0.0010 + $0.0030) = **$280/day**. Total: **$286/day**.

**About 64 percent cheaper than all-Opus.** (Output counts are assumed to include any thinking tokens, which bill as output.) The arithmetic is not exotic; model choice and parameter choice both move the dial materially.

</details>

## Try it yourself: an A/B on the flagship vs the balanced tier

About 20 minutes. You will need the SDK from lesson 1 and an Anthropic API key. Costs are a few cents at most.

**Part A: a 5-question eval set.** Pick or write 5 prompts your application would realistically run. Vary difficulty (one easy, three medium, one hard). Write down the ideal answer for each (or a rubric, e.g., "must mention X, must avoid Y").

**Part B: run both models.** Call each prompt twice: once with `model="claude-opus-5-5"`, once with `model="claude-sonnet-5-5"` (the flagship and balanced tier as of November 2026; check the Models overview for today's IDs). Set effort explicitly on both (for example `output_config={"effort": "medium"}`), because their defaults differ. For each call, log: prompt, model, response, *usage.input_tokens*, *usage.output_tokens*. Compute the per-call cost for each.

**Part C: compare quality.** Score each response 0/1 against your rubric (or 1-3 if you want more granularity). Total the scores per model. If the balanced model matches the flagship on your set, it is the right model for this feature; if the flagship pulls ahead on the hard ones, you have a routing question (flagship for hard cases, balanced tier for easy ones).

<details>
<summary>What you'll get (an example, not the canonical answer)</summary>

On a typical "summarize this paragraph in one sentence" eval, the balanced model often matches the flagship closely; on a "trace through this multi-step reasoning problem" eval, the flagship tends to pull ahead. The right model for your application is the cheapest one that passes your eval, and the only way to know is to run it. Your version of this exercise will look different per task; do not assume the result.

A bonus extension: add a third column for the balanced model at `effort: "low"`. If quality holds, you have a third lever (the same model, less spend per call). This is the kind of micro-optimization that compounds at scale.

</details>
