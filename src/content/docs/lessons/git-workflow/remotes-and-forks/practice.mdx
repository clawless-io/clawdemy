### Self-check questions

Answer in your own words before checking model answers in the cheatsheet.

**Q1.** Explain why git is called "distributed." What does that mean for offline work and for recovering from a GitHub outage?

**Q2.** Walk through what `git fetch` does and how it differs from `git pull`. Why might a senior engineer prefer fetch over pull for daily work?

**Q3.** Your teammate pushed to main while you were committing. You try `git push` and it's rejected. Walk through the resolution in order.

**Q4.** In the fork-based model, what's the difference between `origin` and `upstream`? What does each pointer represent?

**Q5.** When is `git push --force-with-lease` safe to use, and when is it never acceptable?

### Push-pull drill (uses two clones simulating two developers)

This drill simulates two-developer collaboration on a single laptop. Use two folders on your machine.

**Setup:**

1. Create a sandbox folder. `mkdir l8-drill && cd l8-drill`
2. Initialize a "bare" repo (this simulates GitHub): `git init --bare central.git`
3. Clone it as "developer 1": `git clone central.git dev1`
4. Clone it again as "developer 2": `git clone central.git dev2`

You now have three folders: `central.git` (the "remote"), `dev1` (clone 1), `dev2` (clone 2).

**Drill 1: First commits + push:**

1. `cd dev1`. Create a file: `echo "Hello from dev1" > README.md`
2. `git add README.md && git commit -m "Initial commit"`
3. `git push origin main`. (Note: this works even without -u because main already exists locally.)
4. `cd ../dev2 && git pull`. Observe dev2 now has the README.

**Drill 2: Diverging commits + conflict:**

1. `cd dev1`. Edit README.md to add "Line from dev1" at the end. Commit. Push.
2. `cd ../dev2`. Edit README.md (WITHOUT pulling first) to add "Line from dev2" at the end. Commit.
3. Try to push from dev2: `git push`. **Rejected.**
4. Read the error message carefully; notice it tells you to pull first.
5. `git pull --rebase`. Conflict! (L7 territory.)
6. Resolve the conflict (keep both lines). `git add README.md && git rebase --continue`.
7. Push: `git push`. Succeeds.
8. `cd ../dev1 && git pull`. Observe dev1 has the combined README.

**Drill 3: Force-with-lease:**

1. From dev1, edit README and commit. Push.
2. From dev1, IMMEDIATELY rewrite that commit: `git commit --amend -m "Better message"`.
3. Try to push: `git push`. Rejected (history rewritten).
4. `git push --force-with-lease`. Succeeds (you're the last one who pushed, so the lease is intact).
5. From dev2: `git fetch`. Observe the rewritten commit.

**Drill 4: Force-with-lease catches concurrent writes:**

1. From dev1, edit README and commit. Push.
2. From dev2, `git pull --rebase` to get the latest.
3. From dev2, edit README and commit. Push.
4. From dev1, BEFORE fetching, try to amend a commit and force-with-lease:
   - `git commit --amend -m "Trying to rewrite"`
   - `git push --force-with-lease`. **Refused** (dev2 pushed since dev1's last fetch).
5. From dev1, `git fetch` to update your view. Now decide: was the rewrite even valuable? If so, rebase your local on top of dev2's commits, then force-with-lease succeeds.

This drill shows force-with-lease catching the dangerous case. Plain `--force` would have silently destroyed dev2's commit.

### Fork workflow drill (uses a real GitHub fork)

This drill takes you through the open-source contribution workflow end-to-end.

**Drill 5: Set up a fork (real GitHub, about 10 minutes):**

1. Pick a small public repo on GitHub (your own, or a "good first issue" hunt).
2. Click "Fork" in the upper-right of the GitHub UI. GitHub creates `<your-username>/<repo>`.
3. `git clone https://github.com/<your-username>/<repo>.git`
4. `cd <repo>`
5. `git remote add upstream https://github.com/<original-owner>/<repo>.git`
6. `git remote -v`: verify you see both `origin` and `upstream`.
7. `git fetch upstream`: pull down upstream's branches without merging.
8. `git branch -a`: observe `remotes/origin/main` AND `remotes/upstream/main`.

**Drill 6: Sync your fork's main from upstream's main:**

1. `git switch main`
2. `git fetch upstream`
3. `git rebase upstream/main`: update your local main to match upstream
4. `git push origin main`: push the updated main to your fork

Repeat this whenever upstream has moved and you want your fork's main current.

**Drill 7: Make a contribution (simulated):**

1. `git switch -c improvement/example-change`
2. Make a small, low-risk change (a comment, README typo, etc.)
3. Commit with a clear message.
4. `git push -u origin improvement/example-change`
5. Open a PR on GitHub from your fork's branch to upstream's main.
6. If this is a real contribution, address review feedback. If it's just a practice drill, you can close the PR without merging.

You have now performed the full open-source contribution workflow. The same six steps work for almost every public repo on GitHub.

### Flashcards

<FlashcardSet>

<Flashcard question="What is a remote?">
A named pointer to another git repository's URL. `origin` is the default name and usually points to your team's GitHub repo.
</Flashcard>

<Flashcard question="Why is git called distributed?">
Because every clone is a full repository. Every developer's machine has the entire history. There's no architectural "central server"; that's a team convention.
</Flashcard>

<Flashcard question="What does git push -u origin (branch name) do?">
Pushes the branch to origin AND sets the upstream tracking relationship so future `git push` calls work without arguments.
</Flashcard>

<Flashcard question="What's the difference between git fetch and git pull?">
Fetch downloads remote changes but doesn't merge. Pull = fetch + merge (or fetch + rebase, with `--rebase`). Fetch lets you inspect before committing to integrate.
</Flashcard>

<Flashcard question="What is a remote-tracking branch like origin/main?">
A local label pointing to what the remote's branch looked like at your last fetch. You don't commit to these directly; they're read-only snapshots of "what GitHub said."
</Flashcard>

<Flashcard question="What does git status tell you about your branch's relationship to the remote?">
Ahead by N commits (you have commits to push), behind by N commits (remote has commits to pull), or diverged (both have new commits that need merging or rebasing).
</Flashcard>

<Flashcard question="What's the fork-based contribution model?">
`origin` = your fork. `upstream` = the original project. You push to origin, open PR from origin to upstream. This is how almost all open-source contributions work.
</Flashcard>

<Flashcard question="When is git push --force acceptable?">
Almost never. Prefer `--force-with-lease`, which refuses to overwrite if the remote has moved since your last fetch. Even then, only on personal branches; never on shared `main`, `develop`, or release branches.
</Flashcard>

<Flashcard question="What does git config --global pull.rebase true do?">
Sets all future `git pull` calls to use `--rebase` by default instead of merge. Keeps history linear; eliminates the "Merge branch 'main' of ..." commit clutter.
</Flashcard>

<Flashcard question="How does git survive a GitHub outage?">
Mostly fine. Local operations (commit, branch, log, diff, status) work offline. Only push and pull require the network. The team's history is replicated across every developer's laptop; recovery is always possible from any clone.
</Flashcard>

</FlashcardSet>
