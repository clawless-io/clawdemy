### Interactive rebase cleanup drill

1. Create a test repo (`git init test-rebase && cd test-rebase`).
2. Create a file `notes.txt` with one line, commit with message "initial." Add a tag `start`.
3. Make 5 commits, each adding a line:
   - "WIP first attempt"
   - "fix typo"
   - "actually fix"
   - "add another line"
   - "WIP more"
4. Run `git log --oneline` to see your 6 commits.
5. Run `git rebase -i start`.
6. In the todo list, change the actions to: reword first WIP to "add first line," fixup the two typo fixes into it, reword "add another" to "add second line," fixup the final "WIP more" into it.
7. Save. Edit commit messages as prompted.
8. After the rebase, run `git log --oneline` again. You should have 2 clean commits plus the initial.

### Fixup-and-autosquash drill

1. In the same or a fresh test repo, make a commit "add foo function" (just create a file `foo.py` with a placeholder).
2. Note its SHA.
3. Make another commit "add bar function" (`bar.py`).
4. Realize foo.py needs a fix. Edit it. Run `git commit --fixup=<sha-of-foo-commit>`.
5. Make another commit "add baz function."
6. Run `git rebase -i --autosquash <starting-sha>` (the SHA before "add foo function").
7. The editor should pre-fill the fixup action and rearrange. Just save.
8. Verify the fixup got folded into the foo commit.

### Conflict-during-rebase drill

1. Create a fresh repo. Make commit A: file `port.conf` with content "port=8080."
2. Branch `feature/port-9090`. On it, change to "port=9090," commit.
3. Switch back to main. Change to "port=8443," commit.
4. Switch to `feature/port-9090`. Try `git rebase main`.
5. You should hit a conflict.
6. Resolve by keeping main's `port=8443`. Mark resolved with `git add port.conf`.
7. Run `git rebase --continue`.
8. Verify the branch is now based on main with port=8443. The original port=9090 change is effectively dropped (the rebase replayed but the resolution chose main's value).

### Recovery from rebase drill

1. Create a fresh repo. Make 4 commits with distinct messages.
2. Run `git rebase -i HEAD~3` and arbitrarily squash some.
3. Save and complete.
4. Run `git log --oneline` to see the rewritten history.
5. Run `git reflog`. Find the entry just before "rebase (start)."
6. Run `git reset --hard HEAD@{<N>}` to that entry.
7. Run `git log --oneline` again. The original 4 commits should be back.

### Scenario reflections

**Scenario A:** You've been working on a feature branch for a week. Your manager asks you to open a PR today. Your branch has 18 commits, most of them "WIP" or single-word messages. Walk through your approach to preparing the PR.

**Scenario B:** You accidentally ran `git push --force` on main after rebasing it. Three teammates have pulled main today. Walk through the recovery process you'd lead.

**Scenario C:** You're rebasing a feature branch onto main and hitting conflict after conflict: every commit you've made conflicts with main's recent changes. After ten conflicts, you're exhausted. What are your options?

**Scenario D:** You're on a team that uses GitFlow. Someone proposes switching to a "rebase before merge" policy. Discuss the pros and cons.

<Flashcard question="The published-history rule">
Don't rebase commits you've pushed to a shared branch: rewriting breaks teammates' local history.
</Flashcard>

<Flashcard question="git push --force-with-lease">
Force-push only if remote is still at the commit you last fetched: safer than `git push --force`.
</Flashcard>

<Flashcard question="Reflog use case">
Recover from any HEAD-modifying mistake (rebase, reset, hard-deleted branch): records last 90 days of HEAD moves.
</Flashcard>

<Flashcard question="git reset --hard HEAD@(N)">
Return to the Nth-back HEAD state from the reflog (`git reset --hard HEAD@{N}`).
</Flashcard>

<Flashcard question="Rebase vs merge: rebase when...">
Cleaning up local history before PR, team prefers linear log, integrating into a branch nobody else pulls from.
</Flashcard>

<Flashcard question="Rebase vs merge: merge when...">
Branch is published and others pulled, want to preserve parallel-development story, long-lived release branches.
</Flashcard>

Repository setting that forbids force-push to main: most important guardrail against accidental history rewrite.
