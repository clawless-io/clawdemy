**MCP does not make the model smarter. It makes tools reachable.** The **Model Context Protocol (MCP)** is an open standard for connecting AI apps to outside tools and data. After this lesson you can explain what MCP is, name its three roles (host, client, server), name the three things a server offers (tools, resources, prompts), and explain why something like Playwright MCP exists.

**The problem it solves is duplication.** The Stanford lecturer points out that each model could expect tools to be described in its own custom way, so the same tool could have to be built again for each one. MCP gives tools one common way to be presented to models. The official documentation compares it to a USB-C port: build one port, and anything that follows the standard fits.

**It is about the connection, not the model.** The documentation says MCP covers the exchange of context and does not dictate how an app uses its model. In terms of the previous lesson, MCP changes where Stage 2 (running the function) can live: inside a server someone else built, reached through a standard plug. The model's job stays the same.

This summary is the scan-it-in-five-minutes version. The full lesson walks through the lecturer's teddy bear poetry-book example, a step-by-step Playwright MCP illustration, and the official security guidance.

## Core ideas

- **MCP** is a protocol: an agreed set of rules for how two pieces of software talk. The lecturer notes it came from the Anthropic team; the documentation describes it as an open-source standard supported by apps from several companies.
- **The host** is the AI application you use: a chat assistant, a code editor with AI features, a company chatbot.
- **The server** is a program that offers capabilities to AI apps. The lecturer describes it as the program that serves the tools. It is often built by whoever knows the underlying system, such as the company that makes it.
- **The client** lives inside the host and holds the connection to one server. The host creates one client for each server it connects to.
- **A server can run on your own machine, or somewhere on the internet.**
- **The flow.** The client asks the server for its tools, the host hands that list to the model, the model picks a call, the client sends it, the server runs it, and the result goes back into the conversation.
- **The model never talks to the server directly.** It only reads and writes text. The client carries the call and the result.
- **Tools** are actions the model chooses to call, such as searching for flights or sending a message.
- **Resources** are read-only data the app manages, such as file contents or database records.
- **Prompts** are reusable templates that instruct the model. The user picks them; they run when a person chooses them.
- **The control test.** The model chooses tools. The app manages resources. The user picks prompts.
- **The lecturer's example.** A book provider runs a server for recommending the teddy bear a poetry book: tools to find or recommend books, prompts showing how to look up a title or recommend one by taste, resources like the bear's collection or popular books that people buy.
- **Playwright** is browser automation software that programmers drive with code. Its site says: "Playwright enables reliable web automation for testing, scripting, and AI agents."
- **Playwright MCP** is an MCP server built on Playwright. It lets models work with web pages using what it calls structured accessibility snapshots: a text description of the page, with a reference for each element, instead of a screenshot.
- **Who does what.** MCP is the connection. Playwright does the browser work. The model chooses the next step and reads the outcome.
- **MCP is not the only route.** The Playwright MCP documentation also points coding agents to a command-line route it says uses less of the model's context.
- **The specification on safety.** Tools can run arbitrary code and need careful handling. The host app must get your explicit permission before it runs a tool. (In practice, apps can also let you approve some actions ahead of time.) A tool's own description should not be trusted unless its server is trusted.
- **MCP cannot enforce safety on its own.** The apps that use MCP are expected to build consent screens and permission settings. The Playwright MCP documentation states it is not a security boundary.
- **Pitfall: thinking MCP is a tool.** It is the connection standard; a server wraps a system and offers its actions as tools.
- **Pitfall: thinking more servers is always better.** Each one is more software with access to something.

## What changes for you

When a company announces an MCP server, you can read it plainly: their system now has the standard plug, and AI apps that speak MCP can reach it. When someone asks why a tool needs an MCP version, you can separate the tool's own work from the connection. And before you connect a server, you have four questions: who built it, what it can reach, which tools can change things, and whether your app asks before acting.

**MCP does not make the model smarter. It makes tools reachable.**\
**The model asks, the client carries, the server acts.**\
**Plug in only what you trust.**
